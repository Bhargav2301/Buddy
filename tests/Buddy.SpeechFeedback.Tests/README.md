# Local speech feedback repair

The active complete-answer path is MainWindow or VoiceOverlayWindow -> LocalVoiceOutput.SpeakAsync -> SpeechText.CompleteAnswer -> SentencePlayback -> the selected local synthesizer and fixed audio endpoint. The teaching path uses the same complete-answer entry. The optional staged path still accepts independently validated sentences, prepares them once, and uses the existing bounded playback pipeline. AssistantInteraction's old SentenceBuffer is not the current synthesis boundary.

The prior cleanup removed only lowercase HTTP(S) and left several address/citation presentations audible. Cleanup now handles case-insensitive HTTP(S), balanced Markdown destinations, URL-valued labels, WWW/FTP/file addresses, common bare-domain suffixes, reference definitions/links, numeric/footnote/citation markers and encoded markup. Domain-like decimal/version numbers and ordinary bracketed qualifications remain intact. This is bounded presentation cleanup, not arbitrary-format URL recognition, source verification, retrieval or semantic safety assessment. Unusual bare domains without a recognized suffix can still require a written answer. No URL or citation text by itself produces a provenance cue.

`LocalVoiceOutput.SpeakAsync(text, preferences, sourcesAttached: true)` adds one `Sources are attached;` acknowledgement. Only the host that displayed actual attached sources may pass true. Its default is false. It adds no sentence, preserves complete qualifications and removes duplicate standalone model-generated attachment acknowledgements. Screen context alone is not a source attachment. The server retains model-authored source labels so the existing whole-answer repair/rejection still applies. The root owner must thread displayed web evidence from MainWindow and imported knowledge rows from VoiceOverlayWindow; those files are outside this worker's scope.

Complete answers now use one synthesis/playback request. Previously the caller split the answer into separate WAV requests, bypassing the existing Piper worker's pauses between synthesized sentences. One request restores the opportunity for those existing pauses and avoids splitting at abbreviations. This can delay first audio until the full short answer is rendered. It does not change Piper's acoustic model, speaker, rate, preset or engine, and it does not establish human-like sound quality. There was no listening or physical headphone test. The current selected speaker is supplied by the user's preferences, without a hard-coded override.

The 1,600-character synthesis limit remains; a cue that would exceed it refuses speech and keeps the full written answer available. Text is never clipped to meet speech or safety limits. Ordinary model answers still pass the existing maximum-three-sentence and explicit tighter-limit validation. Action plans and approval reviews retain their separate complete review. The staged path remains opt-in and has no inferred source cue. Endpoint selection, microphone policy, cancellation owner, no reroute/fallback, and queued audio clearing remain intact.

The executable test project source-links SpeechText, SentencePlayback and AudioRouteGuard and references the actual service policy. Render/play functions are injected byte-buffer fixtures. Tests cover the reported address variants, shared server-to-speech normalization, host-gated acknowledgement, complete synthesis input, no truncation, late staged refusal, cancellation and selected-route loss during generation gaps. They never create a synthesizer/audio endpoint or access a model, microphone, user profile or desktop window.

```powershell
dotnet run --project tests/Buddy.SpeechFeedback.Tests -c Release -r win-x64 --self-contained true
```

Root integration must separately compile its evidence-threading changes and review the resulting UI flow. Synthetic callbacks and a compile do not establish audible quality, latency, physical output routing or source-link UI acceptance.
